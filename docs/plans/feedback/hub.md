# 쉼터·관계 심화 시스템 (hub) — 1차 검증 피드백 전문

## 김정훈 목사(신학) — 7/10
한줄평: 은혜를 포인트로 팔지 않겠다는 뼈대는 신학적으로 보기 드물게 건전하나, 예수님 배제가 문서 선언에 그치고 코드·테스트로 강제되지 않았으며 예시 대사부터 본문(마 14:30)을 틀리게 인용한 것은 감수위원으로서 그냥 넘길 수 없다.

### 이슈

## 유나(게임 디자인) — 6.5/10
한줄평: 설계 문법은 상급인데 유대 경제 산수가 안 맞고 캠페인 종료 후 허브가 죽는다 — '리텐션 엔진'이라는 간판이 현재 숫자로는 허위 광고.

### 이슈
- [high] 유대 포인트 경제가 자기모순이라 최고 단계 '동행'(24점)에 도달 불가. v1 볼륨(동료당 대사 12개×1점) + 1회성 선물 2~3개 배분이면 동료당 현실적 상한은 14~15점. ①범위에는 '함께한 에피소드로 상승'이라 썼지만 ⑥의 recordEpisodeResult 계약에는 유대 가산이 없다. 게임 제목과 같은 이름의 최종 단계가 도달 불가능한 채 출시되면 컬렉션 게이머는 3일 안에 알아챈다.
  - 제안: 수급원별 유대 획득 시뮬레이션 표를 플랜에 넣어라(대화 n점 + 에피소드 동반 클리어 n점 + 선물 n점 = 단계별 도달 시점). recordEpisodeResult에 '해당 에피소드 참여 동료 유대 +1' 가산을 추가하면 '함께 모험한 만큼 가까워진다'는 테마와도 맞고 24점이 산술적으로 열린다.
- [high] '방문당 once 대사 1개' 가드의 '방문' 경계가 미정의. 허브 퇴장→재입장이 공짜면 문 스팸으로 페이싱 가드가 무력화되고(Hades 플레이어들이 룸 재입장하듯), 엄격히 막으면 '새 대사가 있는 걸 알면서 못 보는' 순수 프러스트레이션. Hades는 재입장 비용이 런 1회라는 자연 앵커가 있었지만 여기는 앵커가 없다.
  - 제안: 방문 카운터를 '에피소드 플레이 1회 완료' 또는 '묵상 날짜 경계 통과'에 묶어 리셋해라. 재입장으로는 안 풀리되, '한 판 더 하고 오면 열린다'는 안내로 허브→에피소드 순환을 오히려 강화할 수 있다.
- [high] 캠페인 종료 후 허브의 수명이 0. once 풀 총량(6인×12개=72개)은 12장 캠페인과 거의 동시에 소진되고, 이후 D30 루프는 '15초 묵상 + bondReward 0 반복 잡담'뿐이다. 리스크 표가 콘텐츠 고갈을 인지하고도 완화책이 '잡담 층'인데, 반복 잡담은 플레이어가 2회차에 즉시 감지하고 허브를 죽은 공간으로 인식한다. 이 플랜의 부제가 '리텐션 엔진'인 것과 정면 충돌.
  - 제안: 둘 중 하나를 명시하라: (a) 허브를 '캠페인 동반 시스템'으로 재포지셔닝하고 리텐션 주장을 빼든가, (b) 포스트 캠페인 콘텐츠 축(주간 회상 대화, 2회차 상위 대사 티어, 에피소드 재도전의 고득점/통찰 해법과 연동된 신규 반응 대사)을 v1 범위에 넣어라. GDD §8의 '낮은 바닥/높은 천장' 재도전이 새 반응 대사를 여는 구조가 가장 싸고 테마에 맞다.
- [high] 실패 구제 대사(시나리오 D)로 가는 라우팅이 없다. 흐름도상 game(실패)→map이고, 3연패로 좌절한 플레이어가 허브 문을 열 트리거가 전무하다. 맵의 쉼터 아이콘 점(selectHasNewDialogue)은 범용 표시라 '지금 마태가 널 도와줄 수 있다'는 신호가 아니다. 가장 필요한 순간에 가장 좋은 콘텐츠가 발견되지 않는 구조.
  - 제안: failedAtLeast 조건 충족 시 맵에서 해당 동료의 얼굴 아이콘이 쉼터 위에 뜨거나, 실패 이탈 화면에 '마태가 할 말이 있는 것 같아요' 한 줄(비강압 톤 유지)을 추가해라. 통합 테스트 17번 옆에 이 라우팅 테스트도 추가.
- [medium] M3의 유일한 능력 연결이 '집중 미터 관대 +10%' — 비지각 패시브다. 관계→능력→'다음 도전이 더 잘 풀림'이라는 코어 루프 약속을 처음 증명하는 순간에 플레이어가 감지할 수 없는 버프를 쓰면, M3 완료 기준('체감 변화 확인')을 스스로 못 넘는다. 라이브옵스에서 배운 것: 보이지 않는 버프는 없는 버프다.
  - 제안: 첫 해금 능력은 가시적으로: 미니게임 화면에 베드로가 실제로 등장해 1회 구조해주는 액티브, 또는 시작 전 '베드로의 조언' 카드 같은 눈에 보이는 개입. 수치 버프는 2번째 이후 능력으로.
- [medium] 선물 시스템의 깊이가 콘텐츠 8종 1회성으로 끝난다. 감점 없음(+2/+1)은 지지하지만, 획득이 1회성 보너스 목표 한정이라 '누구에게 줄까' 결정이 총 8번뿐이고, favored 여부를 사전에 알 수 없어 +2를 +1로 '낭비'한 순간이 영구 최적화 실패로 남는다. 감점만 없앴지 손실 회피는 남아 있다 — 컬렉션 게이머는 결국 위키를 편다.
  - 제안: 선호를 사전 대화에서 자연스럽게 텔레그래프해라('빌립이 요즘 보리빵 얘기를 자주 한다' 류의 잡담). 낭비 불안이 사라지면 위키 없이 게임 안에서 결정이 완결된다. 인벤토리 '중복 허용 배열'도 획득이 1회성이면 모순이니 정리.
- [medium] D1 재방문의 콘텐츠 밀도가 너무 얇다. 에피소드 1개 클리어 상태면 D1에 볼 것은 동료 2인×드립 1개 + 15초 묵상 = 90초 남짓. 시나리오 B가 그리는 '목표 구배' 감각은 대사 체인의 글빨에 전적으로 의존하는데, 페이싱 가드가 오히려 D1 세션을 굶긴다.
  - 제안: D0~D3 온보딩 구간만 가드를 완화(방문당 2개)하거나, D1 한정 신규 콘텐츠(첫 묵상의 특별 연출, 첫 유대 레벨업이 D1에 오도록 임계 3점 튜닝)를 배치해 초기 리텐션 절벽을 메워라.
- [low] 묵상 보상 '등불 기름'이 순수 연출용 — 아무 데도 안 쓰이는 재화는 무보상보다 나쁘다. 플레이어가 '이 게임의 보상은 가짜'라고 학습하면 다른 보상(로어, 능력)의 가치 인식까지 깎인다.
  - 제안: 미미하되 실재하는 용처 하나: 쉼터 모닥불/등불의 밝기·장식이 기름 누적으로 은은히 변한다(허브 공간의 시각적 성장). 파워와 무관하니 초대 원칙도 안 깨진다.
- [low] 플레이테스트 합격 기준의 통계적 근거 부족 — 5~8명 표본으로 '80% 이상 자발 언급', '죄책감 0명' 같은 임계는 1명 차이로 뒤집힌다. 기준 자체는 옳은 방향이나 n이 너무 작아 합격/불합격 판정이 노이즈다.
  - 제안: MVP 단계는 정량 임계 대신 정성 관찰 프로토콜(발화 녹취 코딩)로 바꾸고, 정량 임계는 v1 베타(n≥30)로 미뤄라.

## 박도윤(엔지니어링) — 7/10
한줄평: 실제 코드를 읽고 쓴 티가 나는, 1인 개발 규모에 맞는 드문 플랜이다 — 다만 세이브 마이그레이션 설계가 현재 store.ts 구현과 정면 충돌하고, 잡담 대사 무한 파밍 구멍과 jsdom에서 불가능한 테스트 2개 등 '디테일에서 터질' 지뢰가 그대로 박혀 있다.

### 이슈
- [high] persist 마이그레이션 설계가 현재 코드와 충돌한다. 실제 store.ts는 name: 'donghaeng-save-v1'로 버전을 스토리지 키 이름에 박아놨고 version 옵션 자체가 없다(암묵 version 0). 플랜은 "donghaeng-save-v1 → v2 + zustand version/migrate"라고 쓰는데, 키 이름을 v2로 바꾸면 zustand migrate는 아예 발동하지 않는다 — migrate는 같은 키 안의 version 번호 간에만 동작한다. 키를 바꾸는 순간 기존 유저 세이브는 조용히 버려지고, 이건 플랜 스스로 '신뢰 파괴'로 규정한 사고다.
  - 제안: 키는 'donghaeng-save-v1' 그대로 두고 version: 2 + migrate 함수로 간다(키의 v1은 이제 의미 없는 화석으로 인정). 또는 부팅 시 구 키 → 신 키 수동 복사 코드를 M0 산출물로 명시. 어느 쪽인지 플랜에 한 줄로 확정하고, 테스트 16번에 '구 키에 v1 데이터가 있는 상태에서 신 스토어 부팅' 시나리오를 추가하라.
- [high] 잡담(idle) 대사 무한 유대 파밍 구멍. DialogueEntrySchema에서 bondReward 기본값이 1인데 once:false 잡담은 무한 반복 가능하다. 테스트 8번이 '잡담은 bondReward 0이다'라고 주장하지만 이는 콘텐츠 작성자가 매번 bondReward:0을 손으로 써줘야만 성립하는 관례이지 스키마가 보장하지 않는다. 한 명이라도 빠뜨리면 같은 대사 반복 탭으로 유대 24점(만렙)까지 노가다 가능 — 플랜이 스스로 배제한다던 '호감작 그라인드'가 기본값에서 열린다.
  - 제안: 스키마에 .refine(e => e.once || e.bondReward === 0) 을 걸어 once:false && bondReward>0 조합을 Zod 파싱 단계에서 거부하거나, 엔진에서 !once면 bondReward를 무시하도록 dialoguePool 계약에 명시하고 그걸 테스트 8번의 실제 검증 대상으로 바꿔라.
- [high] 유대 24점(4단계 '동행') 도달이 v1 콘텐츠 볼륨으로 산술적으로 불가능하거나 아슬아슬하다. 수급원은 대화(기본 +1)·선물(+1/+2)·'함께한 에피소드'인데, ①동료당 대사 12개 = 최대 12점, ②선물 8종을 전부 한 명에게 몰아줘도 +16이지만 favored는 소수, ③'함께한 에피소드로 상승'은 §⑥ 액션 표 어디에도 가산 경로가 없다 — recordEpisodeResult는 lastPlayed만 갱신한다. 스펙에 쓰인 세 번째 수급원이 인터페이스에서 증발했고, 그거 없이는 threshold 테이블이 도달 불가능한 장식이다.
  - 제안: recordEpisodeResult(또는 completeEpisode)에 '참여 동료 bond +1' 가산을 계약으로 추가하고, 동료 1인 기준 수급 총량 계산표(대화 12 + 에피소드 n + 선물 기대치)를 ③에 넣어 threshold 0/3/8/15/24가 실제 도달 가능한지 검산하라. 검산 없는 threshold는 전부 재조정 대상이다.
- [medium] "감수 미승인 콘텐츠는 컴파일 타임에 제외"가 반쪽짜리다. JSON 메타(DialogueEntry)는 review 필터로 걸러도, M6 이후 대사 본문은 hub.ink 하나를 통째로 컴파일한 hub.ink.json에 산다. draft knot의 텍스트 전문이 프로덕션 번들에 그대로 실려 나가고, 번들 까보면 읽힌다. '감수 누락이 배포되는 사고를 구조적으로 차단'한다는 주장이 정확히 지켜야 할 지점(신학적으로 미검수된 문장의 배포)에서 뚫려 있다.
  - 제안: 빌드 스텝에 ink 후처리 추가: 승인된 entry의 inkKnot 목록을 화이트리스트로 삼아 미승인 knot를 ink 소스에서 스트립한 뒤 컴파일. 겸사겸사 JSON의 inkKnot ↔ 실제 knot 존재 여부 검증(참조 깨짐 = 빌드 실패)도 같은 스텝에서 공짜로 얻어라 — 현재 플랜에는 이 드리프트 검증이 아예 없다.
- [medium] completeEpisode와 recordEpisodeResult 이중 호출 계약은 5개 미니게임 × 클리어/실패/중도이탈 경로마다 사람이 기억해야 하는 규칙이다. 현재 WaterWalkGame만 봐도 실패 시 컴포넌트 로컬 fails만 증가하고 재도전은 언마운트 없이 start()로 도는 구조라, ← 버튼 이탈 시 setScreen('map')만 호출된다 — failStreak을 어디서 기록할지 통합 지점이 코드에 존재하지 않는다. 중도 이탈이 실패로 카운트되는지도 미정의.
  - 제안: 액션을 finishEpisode(episodeId, {cleared, failed}) 하나로 통합해 completed/companions/lastPlayed/failStreak을 원자적으로 갱신하고, 기존 completeEpisode는 그 안으로 흡수하라. '중도 이탈은 failStreak 미증가'(관대 원칙과 일관) 같은 판정 규칙을 §⑥ 표에 명문화할 것.
- [medium] 테스트 20(prefers-reduced-motion 시 pulse 정지)과 21(모든 히트박스 ≥44×44 자동 검사)은 RTL/jsdom에서 검증 불가능하다. jsdom은 레이아웃 엔진이 없어 getBoundingClientRect가 전부 0을 반환하고, CSS 미디어 쿼리에 따른 animation 적용 여부도 렌더링되지 않는다. 이대로 구현하면 '항상 통과하는 가짜 테스트'가 되어 접근성 회귀를 놓친다.
  - 제안: 20·21번을 Playwright(실브라우저) 계층으로 명시 이동하거나, 21번은 '--touch 토큰 미사용 인터랙티브 요소 lint' 같은 정적 검사로 대체하라. 테스트 계획에 도구 계층(Vitest/RTL/Playwright) 구분을 추가할 것.
- [medium] failedAtLeast 조건 스키마가 상태 모델과 안 맞는다. 조건은 임의의 episodeId를 지정할 수 있지만 상태는 lastPlayed 단일 객체에만 failStreak을 들고 있다. 마태 힌트 대사가 ep10 3연속 실패를 조건으로 걸었는데 플레이어가 ep10 2번 실패 → ep07 클리어 → 쉼터 방문하면 failStreak 컨텍스트가 통째로 증발한다. '직전 에피소드'만 의미 있는 조건인데 스키마는 전 에피소드를 약속하는 과대 표현.
  - 제안: 둘 중 하나로 정합: (a) failedAtLeast에서 episodeId를 빼고 'lastPlayed 기준'으로 좁혀 스키마가 실제 능력만 약속하게 하거나, (b) failStreaks: Record<episodeId, number>로 상태를 확장. 1인 개발이면 (a)를 권한다 — 힌트 대사의 UX 목적상 직전 에피소드면 충분하다.
- [low] "미니게임은 selectAbilityActive 한 개로만 결합"이라는 계약 원칙이 같은 문서 §⑥ 표와 모순된다. 미니게임은 grantGift(선물 id와 보너스 목표를 알아야 함)와 recordEpisodeResult도 호출한다. 읽기 1 + 쓰기 2, 실제 결합점은 3개다.
  - 제안: 원칙 문구를 '읽기는 selectAbilityActive 하나, 쓰기는 finishEpisode·grantGift 두 액션'으로 정직하게 고쳐라. 과장된 계약 문구는 나중에 코드 리뷰 기준으로 못 쓴다.
- [low] meditationClock의 '기기 로컬 03:00 경계'와 상태 주석의 'YYYY-MM-DD(로컬)'가 미세하게 어긋난다. 03:00 경계면 저장되는 값은 달력 날짜가 아니라 3시간 시프트된 '논리적 날짜'인데 이 정의가 문서에 없어, 구현자가 new Date().toISOString().slice(0,10)류(UTC 날짜!)를 쓰는 고전적 실수를 할 여지가 있다.
  - 제안: logicalDate = format(now - 3h, 'yyyy-MM-dd', 로컬 타임존) 정의를 ③ 주석에 박고, 테스트 13에 자정~03:00 사이 완료 케이스(전날 논리 날짜로 기록되는지)를 추가하라.
- [low] DialogueEntrySchema 스케치에서 "false면 조건 만족 시 반복 등장하는 '잡담'" 주석이 once가 아니라 conditions 필드 위에 붙어 있다. 사소하지만 이 스케치가 그대로 schema.ts에 복붙될 문서라는 점에서, 주석 위치 오류는 후임(=미래의 나)에게 오독을 유발한다.
  - 제안: 주석을 once 필드로 이동. M0에서 스키마 옮길 때 문서 스케치와 실코드의 diff를 0으로 유지하라.
- [low] 저가 안드로이드 성능은 대체로 안전한 설계지만(정적 배경+소수 스프라이트), 기존 .pulse 키프레임이 filter: brightness를 애니메이션한다 — 등불 점을 동료 6인 + 묵상 등불에 동시에 달면 저가 기기에서 filter는 합성 레이어를 못 타고 매 프레임 래스터라이즈를 유발할 수 있다.
  - 제안: 등불 점 pulse는 opacity/transform만으로 재작성(둘 다 컴포지터 처리 가능). 어차피 §⑦에서 pulse를 새로 정의하므로 지금 고치는 게 공짜다.

### 필수 수정
- 세이브 마이그레이션 경로 확정: 스토리지 키를 'donghaeng-save-v1' 그대로 두고 zustand version: 2 + migrate를 쓰든, 구 키 → 신 키 부팅 시 복사 코드를 넣든 하나로 결정해 M0에 명문화하라. 현재 플랜대로 키 이름만 v2로 바꾸면 migrate가 발동하지 않아 기존 세이브가 전부 유실된다.

## 이서연(UX·접근성) — 7/10
한줄평: 죄책감 제로·다크패턴 제로 설계와 토큰 정합성은 동종 플랜 중 최상급이나, WCAG를 '44px와 pulse 하나'로 축소 해석했다 — 게이지 트랙은 사실상 보이지 않고(1.26:1), 스크린리더는 존재 자체가 언급되지 않는다.

### 이슈
- [high] 유대 게이지 트랙 --line-soft는 rgba(236,231,218,0.09)로, --panel 위 합성 시 약 #283147이 되어 배경 대비 1.26:1에 불과하다. WCAG 1.4.11(비텍스트 UI 3:1) 명백 위반이며, '목표 구배'가 핵심 동기 장치인데 저시력·고령 사용자는 게이지의 전체 길이(끝점)를 인지할 수 없다 — 채움(--lamp)만 보이고 '얼마나 남았는지'가 사라진다.
  - 제안: 게이지 트랙 전용으로 알파 0.25~0.3 수준의 토큰(예: --track)을 1개 신설하거나 1px 외곽선을 병행해 트랙 vs 배경 ≥3:1을 확보하고, ⑨-21처럼 대비 자동 검사를 테스트에 추가하라.
- [high] 스크린리더·접근성 트리에 대한 언급이 문서 전체에 0건이다. '새 대사 등불 점'(상태 정보), 유대 게이지(진행률), UnlockToast(동적 알림)는 전부 시각 전용으로 설계되어 있다. WCAG 1.1.1/4.1.2 관점에서 점은 텍스트 대체가, 토스트는 aria-live가, 게이지는 role=progressbar+값이 필요하다.
  - 제안: ⑥의 셀렉터 계약처럼 '접근성 계약' 절을 신설: CompanionSpot에 aria-label('베드로, 새 대화 있음'), BondBadge에 progressbar 시맨틱, UnlockToast에 polite live region을 명세하고 통합 테스트에 접근성 트리 검사를 추가하라.
- [high] 모션 민감성 대응이 '등불 pulse' 하나에만 명시·테스트(⑨-20)된다. 모닥불 radial-gradient(사실상 깜빡임 연출 유혹이 큰 요소), 묵상의 '15초 잔잔한 연출', UnlockToast의 Motion 글로우는 prefers-reduced-motion 처리가 미명세다. 특히 묵상 15초 연출은 스킵 가능 여부도 불명 — 강제 대기라면 8세 아동 이탈점이자 WCAG 2.2.2(일시정지·건너뛰기) 문제다.
  - 제안: '모든 Motion 사용처는 reduced-motion 시 정적 폴백'을 ⑦의 전역 규칙으로 승격하고, ⑨-20을 모닥불·묵상·토스트로 확장하라. 묵상 연출은 탭으로 즉시 구절 표시 상태로 스킵 가능하게 명시하라.
- [medium] '등불' 메타포가 3중으로 겹친다: ①새 대사 등불 점 ②묵상 등불 ③보상 '등불 기름'. 셋 다 --lamp 계열 색을 쓰는데 의미는 전부 다르다. 게다가 등불 기름은 '연출용'이라며 용도가 정의되지 않은 보상이다 — 8세 아동과 70대 모두 '이게 뭐에 쓰는 거지?'라는 미해결 질문을 안게 되고, 용도 없는 재화는 신뢰를 갉아먹는다.
  - 제안: 메타포를 최소 2개로 분리(예: 새 대사는 말풍선 형태, 묵상만 등불 유지)하고, 등불 기름은 용도를 정의하거나(쉼터 밝기 연출 누적 등 시각적 피드백) 아예 제거하라.
- [medium] DialogueOverlay가 '탭으로 진행'뿐이다. 텍스트 속도 조절, 지나간 대사 다시 보기(백로그), 연타 오탭으로 대사를 놓쳤을 때의 회복 수단이 전무하다. 아동의 연타 습관과 고령자의 더블탭 오입력 모두에서 1회성(once) 드립피드 대사를 영영 놓치는 사고가 난다 — 콘텐츠가 희소한 설계일수록 치명적이다.
  - 제안: 대사 로그(스크롤백) 필수 + 라인 전환에 최소 300ms 입력 디바운스 + 본 대사는 스크랩북/로그에서 재열람 가능하게 하라.
- [medium] 동적 타입(글자 크기 조절)이 '묵상 구절'에만 명시된다. 정작 체류 시간이 가장 긴 대화 오버레이 본문, 유대 라벨, 선물 설명은 크기 조절 언급이 없다. 70대 사용자에게 본문 텍스트 확대는 묵상 화면 하나로 끝나는 문제가 아니다.
  - 제안: 앱 전역 폰트 스케일 설정(rem 기반, 최소 1.0~1.4x)을 ⑦에 전역 규칙으로 추가하고, 오버레이가 확대 시에도 44px 타깃과 줄바꿈을 유지하는지 통합 테스트를 추가하라.
- [medium] 쉼터 첫 방문 온보딩(FTUE)이 없다. 시나리오 A는 '등불 점을 보고 탭한다'를 자명하다고 가정하지만, 점·게이지·선물 시트·묵상 등불이 한 화면에 동시 등장하는 신규 개념 4종이다. 8세와 70대는 발견 학습에 의존시키면 안 되는 대표 집단이다.
  - 제안: M1 완료 기준에 '첫 방문 시 1개 요소만 활성(베드로 점 하나), 나머지는 순차 개방' 같은 점진 공개(progressive disclosure) 시퀀스를 포함하고, 플레이테스트에 '무설명 첫 탭 성공률' 지표를 추가하라.
- [medium] 성찰 프롬프트가 자유 텍스트 입력이다. 건너뛰기는 있지만, 8세 아동·저문해력 사용자에게 '쓰거나 스킵' 양자택일은 사실상 스킵 강제다. 또한 notes: Record<string,string>은 상한 없이 localStorage에 누적된다.
  - 제안: 입력 대안으로 1탭 응답(마음 상태 아이콘 3~4개 선택)을 병행 제공하고, notes에 보관 상한 또는 요약 저장 정책을 명시하라.
- [low] --dawn(#E98A6B)과 --lamp(#F0B24A)는 적록색각(deuteranopia)에서 둘 다 탁한 황토색 계열로 수렴한다. 화자명 강조와 해금·선호 연출이 색상 차이에만 기대면 구분이 약해진다. 또 '새 대사 점'의 2px 링은 크기 명세가 없어 고DPI 소형 기기에서 저시력 사용자가 놓치기 쉽다.

## 민준(비신자 게이머) — 6/10
한줄평: 엔진 설계는 하데스 흉내를 제대로 냈는데, 채울 콘텐츠가 하데스의 0.5%라서 2주면 마르는 우물이고, 매일 오라는 유일한 이유가 '성경 구절 읽기'라는 게 나 같은 사람한텐 치명적이다.

### 이슈
- [high] 유대 포인트 수지 계산이 안 맞는다. 4단계 '동행'은 24포인트인데, v1 볼륨이 동료당 대사 12개(기본 bondReward 1) + 선물 8종을 6명이 나눠 갖는 구조다. 대사 12 + 선물 2개 받아봐야 최대 16~17포인트. 스키마의 HubState와 recordEpisodeResult 어디에도 '함께한 에피소드'로 유대가 오르는 액션이 없는데 §①과 GDD는 에피소드도 유대 수급이라고 써놨다. 지금 숫자대로면 만렙 도달이 수학적으로 불가능하거나, 문서끼리 서로 다른 말을 한다.
  - 제안: recordEpisodeResult에 유대 가산을 명시하고(예: 해당 에피소드 등장 동료 +1), 동료별 '획득 가능 총 포인트 ≥ threshold×1.3' 검증을 콘텐츠 린트(테스트 22번)로 추가하라.
- [high] 콘텐츠 고갈을 리스크로 적어놓고 완화책이 사실상 '더 천천히 굶기기'다. 하데스는 대사 2만 라인 이상인데 v1 목표가 6인×12개=72개. 방문당 1개 가드로 아껴 먹여도 성실한 유저 기준 열흘이면 바닥이고, 그 뒤 쉼터는 '점 안 뜨는 빈 화면'이 된다. 원신 이벤트 하나 분량을 상시 리텐션 엔진이라고 부르는 셈.

- [medium] 묵상 15초 강제 연출 + 성찰 프롬프트는 이틀째부터 스킵 연타 대상이다. '완료보다 구절 체류 시간을 UX 중심에'라는데 체류를 강제하면 그게 바로 설교고, 안 하면 지표가 무의미해지는 자기모순을 문서가 해소하지 않았다.
  - 제안: 연출 스킵을 1탭으로 허용하고, 체류 시간은 KPI가 아니라 관찰 지표로만 두라. 억지로 붙잡는 순간 '벌칙 없음' 설계가 무색해진다.
- [low] '쉼터에 다시 가고 싶다 평균 4.0/5'를 n=5~8로 재는 건 통계가 아니라 분위기다. 한 명만 후하게 줘도 통과된다.
  - 제안: 수치 합격선 대신 행동 지표(테스트 세션 중 자발적 재방문 횟수)를 주 기준으로 삼아라.
- [low] 실패 힌트 대사(시나리오 D)가 '3회 실패 후 쉼터 방문'을 전제하는데, 빡친 유저는 쉼터에 안 가고 앱을 끈다. 힌트가 필요한 순간과 힌트가 있는 장소가 어긋나 있다.
  - 제안: 3연패 시 맵/게임오버 화면에서 '마태가 할 말이 있는 것 같다' 같은 유도 한 줄을 넣어 허브로 연결하라(강요 말고 표시만).
