# 콘텐츠 데이터·세이브 인프라 (data-save) — 1차 검증 피드백 전문

## 김정훈 목사(신학) — 6.5/10
한줄평: 신학을 코드로 강제하려는 발상은 옳고 귀하나, 정작 그 그물에 '예수님 카드화'와 '감수 무효화'라는 큰 구멍이 뚫려 있어 감수위원 서명은 아직 못 준다.

### 이슈
- [high] superRefine 규칙 목록(§3.1)에 'holy 캐릭터가 rewards.companions에 등장하면 에러'만 있고, card.characterId가 holy를 참조하는 경우의 차단이 없다. CharacterSchema 주석은 '스크랩북에 카드로 존재하지 않는다'고 해놓고 검증 규칙에서 빠졌다. 카드는 rewards를 거치지 않고 cards.json에 직접 저작되므로, 이 구멍으로 '예수님 카드'가 스크랩북에 들어갈 수 있다 — 주님을 수집 대상화하지 않겠다는 핵심 신학 원칙이 정확히 여기서 뚫린다.
  - 제안: superRefine에 'card.characterId가 kind:holy 캐릭터를 참조하면 에러'를 명시 추가하고, 테스트 케이스(예수님 카드 저작 시도 → 거부)를 스키마 테스트에 넣어라.
- [high] 예수님 캐릭터의 id가 반드시 kind:'holy'여야 한다는 고정 검증이 없다. 저작자가 실수로든 고의로든 예수님을 kind:'companion'이나 'encounter'로 등록하면 holy 관련 모든 게이트(수집 금지·카드 금지)가 통째로 무력화된다. 또한 bonds(관계 레벨) 배열이 holy 캐릭터에 붙는 것을 금지하지 않아, 예수님과의 관계를 '호감도 수치'로 환원하는 길이 열려 있다 — 신앙을 게이지로 만드는 것은 통합측 감수에서 통과 못 한다.
  - 제안: 예수님 id를 상수(예: 'jesus')로 고정하고 '해당 id는 kind:holy 필수' + 'holy는 bonds/skill 필드 보유 금지'를 superRefine으로 강제하라. deepenBond 액션도 holy id 거부.
- [high] ReviewSchema에 감수자(reviewer)·감수일(reviewedAt)·승인 대상 콘텐츠 해시가 없다. approved 도장을 받은 뒤 대사나 story 문구를 수정해도 승인 표식이 그대로 남는다. 감수를 데이터로 만들겠다는 시스템에서 '승인 후 변경이 감수를 무효화하는' 메커니즘이 없는 것은 서명란 없는 감수 확인서다. 30년 감수 경험상 이 구멍으로 반드시 사고가 난다.
  - 제안: ReviewSchema에 reviewer/reviewedAt/approvedContentHash를 추가하고, 빌드 파이프라인에서 현재 콘텐츠 해시와 승인 해시가 다르면 자동으로 needs-review로 강등(빌드 경고→strict 시 에러)하라.
- [high] T6 감수 게이트가 review.status !== 'approved' 콘텐츠를 v1 출시 빌드에서만 에러로 승격하고, 그 전까지는 '경고 목록'만 출력한다. GDD §2가 '통합측 감수 필수'로 못박은 예수님 실묘사 장면(jesus-depiction)과 수난(passion)조차 MVP~v1 사이의 실제 배포 빌드에 미감수 상태로 실릴 수 있다. 경고는 무시되기 마련이다 — 미감수 예수님 묘사가 단 한 번이라도 배포되면 그것이 곧 사고다.
  - 제안: sensitive에 'jesus-depiction' 또는 'passion'이 포함된 콘텐츠는 MVP 첫 배포 빌드부터 approved가 아니면 빌드 실패로 하라. --strict-review를 전면 적용하는 것은 v1이어도 되나, 이 두 태그만큼은 예외 없이 즉시 적용해야 한다.
- [medium] T4가 'ink 대사 전체 감수 필요'라 해놓고 정작 ReviewSchema는 에피소드·캐릭터·카드 메타에만 붙는다. 대사 본문이 사는 .ink 파일/knot 단위의 감수 상태가 데이터 모델에 없다. '본문이 흐르는 배관'을 자처하는 시스템에서 정작 본문(대사)이 배관의 감수 추적 밖에 있다. 분기 선택지의 교리적 정답/오답 구도, 유다·바리새인 대사의 동기 묘사는 knot 단위로 봐야 하는 감수 대상이다.
  - 제안: ink 파일 또는 knot 단위 감수 메타(파일별 review 블록 + 파일 해시)를 매니페스트에 포함시키고 --review-report가 knot 단위 미감수 목록을 산출하게 하라.
- [medium] verseRef가 실제로 검증하는 것은 책 이름뿐이다. ref가 자유 문자열이라 '마가복음 17장'(마가는 16장까지) 같은 존재하지 않는 장절이 통과하고, display가 book/ref와 독립된 자유 문자열이라 표기 불일치·오표기가 가능하다. '본문 충실성을 스키마가 보증한다'는 주장에 비해 검증 실체가 얕다.
  - 제안: ref에 형식 정규식 + 복음서별 장 수 상한(마태 28·마가 16·누가 24·요한 21) 범위 검증을 넣고, display는 저작 입력이 아니라 book+ref에서 파생 생성하라.
- [medium] sensitive 태그 부여가 전적으로 저작자 자율이다. 예수님이 등장하는 장면에 jesus-depiction 태그를 붙이는 것을 잊으면 감수망을 그냥 통과한다. 기계적 강제를 표방하면서 가장 민감한 분류가 사람의 성실성에 의존한다.
  - 제안: 빌드 스크립트가 ink 태그(# speaker: 등)와 장면 데이터를 스캔해 예수님 등장 knot을 자동 검출하고, sensitive 태그 누락 시 경고(strict 시 에러)를 내는 휴리스틱 검사를 추가하라.
- [medium] 9장 비유 속 인물(탕자, 선한 사마리아인 등)과 역사적 실존 인물(베드로, 마리아)을 CharacterSchema의 kind 체계가 구분하지 않는다. 비유의 등장인물 카드가 'encounter'로 실존 인물과 같은 스크랩북에 섞이면, 특히 10대 플레이어에게 비유(예수님이 지어 말씀하신 이야기)와 실제 사건의 경계가 흐려진다. 이것은 성경 문해 교육의 기본 문제다.
  - 제안: kind에 'parable-figure'를 추가하거나 카드 set 체계('parable')와 연동해 UI에서 '예수님이 들려주신 이야기 속 인물'임을 명시 구분하라.
- [low] gentleMode가 GameSave.settings에 있으나 접근성(난이도 완화)용인지 수난 장면 묘사 수위 조절용인지 정의가 없다. T5가 '전 연령 기준'이라 하면서 수위의 데이터 표현(vignette config의 수위 파라미터 등)이 없어 감수자가 무엇을 기준으로 수위를 판정할지 모호하다.
  - 제안: gentleMode의 역할 범위를 명시하고, 수난 vignette의 연출 지시(텍스트·사운드·화면 효과)를 감수 가능한 데이터 필드로 노출하라.
- [low] 요한복음 7:53-8:11(간음한 여인), 마가복음 16:9-20(긴 결말) 등 사본학적 논쟁 본문의 인용 정책이 플랜 어디에도 없다. verseRef가 4복음서 안이기만 하면 통과하므로, 향후 콘텐츠 확장 시 논쟁 본문이 무정책 상태로 들어올 수 있다.
  - 제안: 신학 체크포인트에 '본문비평 논쟁 구절 사용 시 감수 협의 필수' 항목을 추가하고, 해당 구절 범위를 데이터로 등록해 자동으로 needs-review 처리하라.

### 필수 수정
- superRefine에 'card.characterId → kind:holy 참조 금지' 규칙을 명시 추가 — 예수님 카드가 스크랩북에 들어갈 수 있는 현재의 구멍을 막을 것 (테스트 케이스 포함)
- 예수님 id 고정 + 'holy 필수, bonds/skill 보유 금지' 스키마 강제 — 예수님이 companion/encounter로 등록되거나 관계 게이지 대상이 되는 경로를 원천 차단할 것
- ReviewSchema에 reviewer·reviewedAt·승인 시점 콘텐츠 해시를 추가하고, 승인 후 콘텐츠 수정 시 자동 needs-review 강등 메커니즘을 파이프라인에 넣을 것
- sensitive가 'jesus-depiction' 또는 'passion'인 콘텐츠는 v1이 아니라 MVP 첫 배포 빌드부터 approved 아니면 빌드 실패로 게이트를 앞당길 것
- ink 대사(knot/파일 단위)의 감수 상태를 데이터 모델에 편입할 것 — 현재 감수 추적이 메타데이터에만 걸리고 정작 본문은 사각지대
- verseRef의 장·절 실재 검증(복음서별 장 수 상한)과 display 파생 생성으로 본문 참조 오기를 기계적으로 차단할 것

## 유나(게임 디자인) — 6.5/10
한줄평: 세이브 배관은 시니어급으로 탄탄한데, 정작 그 위로 흘려보낼 리텐션 엔진의 데이터(허브 드립피드 추적, 에피소드 내 재개 위치, 세션 간 난이도 기억)가 스키마에 없어서 D8–30 루프가 데이터 계층에서 끊긴다.

### 이슈
- [high] GameSave에 '에피소드 내 장면 진행 위치'가 없다. lastEpisode는 string | null뿐이고 scenes는 시퀀스(dialogue→minigame→dialogue)로 정의됐는데, 장면 2까지 끝내고 이탈하면 재개가 에피소드 처음이다. S6은 'ink 대화 그 지점 복원'을 약속하면서 정작 '몇 번째 장면인지'는 저장 안 한다 — 이미 깬 미니게임을 다시 시키는 순간 보상 리듬(10–15분 마일스톤)이 재탕 노동으로 바뀌고, 이게 모바일 이탈의 고전 패턴이다.
  - 제안: GameSave에 sceneProgress: Record<episodeId, number>(완료한 장면 인덱스)를 추가하고 selectResumePoint가 episodeId+sceneIndex를 반환하게 계약을 고쳐라. 장면 경계 = 저장 경계라는 §5.3 원칙과도 일관된다.
- [high] 리텐션 엔진(Hades 드립피드 허브)의 데이터가 통째로 비어 있다. bonds는 level+inkKnot뿐이고, '상황 반응형 대사 조건'은 부록 열린 질문 #3으로 미뤄졌으며, deepenBond(characterId)는 무엇이 레벨업을 트리거하는지(페이싱 자원·쿨다운·방문당 1회 제한) 정의가 없다. D8–30 리텐션을 전부 짊어질 시스템인데, '스키마는 초반에 확정, 나중에 바꾸면 비쌈'(GDD §11)이라던 원칙에서 가장 비싼 부분만 빠졌다. 허브에 갔는데 새 대사가 없는 날이 이틀 연속되면 그 유저는 돌아오지 않는다.
  - 제안: bonds 항목에 최소한 조건 스키마(requires: {episodes?, insights?, minLevel?}, cooldown, priority)와 레벨업 페이싱 규칙(예: 에피소드 클리어당 심화 기회 n회)을 지금 정의하라. 내러티브 플랜 합의 전이라도 필드 자리는 v2에 박아야 마이그레이션 비용이 안 생긴다.
- [high] '본 허브 대사' 추적이 hub.ink의 ink state에 암묵적으로 들어가는 구조인데, R3의 완화책이 'ink state 복원 실패 시 시작점 폴백 + 클리어분 정리'다. 허브는 에피소드와 달리 영구히 자라는 단일 스토리라서, .ink가 바뀌는 매 콘텐츠 업데이트마다 복원이 깨질 확률이 가장 높고, 폴백되는 순간 '이미 본 대사 재노출'로 드립피드의 신선함이 붕괴한다. 진행 자산은 game에 있어 무손실이라는 R3의 논리가 허브에는 성립하지 않는다.
  - 제안: '본 대사(knot id) 집합'을 ink 변수가 아니라 GameSave.seenKnots 같은 내구 필드로 승격하고, 허브 ink는 매 방문 stateless로 진입해 외부 함수로 seen 여부를 조회하게 하라. ink state 저장은 에피소드 대화에만 한정.
- [high] 세이브 쓰기 경로가 이중이다. storage.ts(Zustand persist용 비동기 StateStorage)와 autosave.ts(스토어 구독→디바운스 커밋)가 둘 다 존재하는데, SaveFile은 checksum·updatedAt을 포함한 단일 레코드다. persist가 game 조각을 독립적으로 쓰면 checksum이 어긋나고, 두 쓰기 경로의 경합은 테스트 #13(체크섬 변조 감지)을 정상 플레이에서 오탐시킬 수 있다 — '파일이 손상된 것 같아요'를 멀쩡한 유저에게 보여주는 순간 신뢰 설계 전체가 무너진다.
  - 제안: 쓰기 소유자를 하나로 확정하라. 권장: persist 미들웨어를 버리고 autosave.ts가 유일한 컴포저(스토어 스냅샷+ink+checksum → save:current 원자 쓰기)가 되며, storage.ts는 읽기 전용 hydrate 유틸로 격하.
- [medium] DDA(ENGAGEMENT §3 '연속 실패 시 슬쩍 관대')의 세션 간 기억이 없다. 미니게임 내부 상태는 휘발 원칙이라 실패 스트릭도 같이 증발하는데, 그러면 좌절해서 앱을 끈 유저가 다시 열었을 때 정확히 같은 난이도를 다시 만난다 — 이탈 직전 유저에게 가장 관대해야 할 순간에 리셋되는 역설. gentleMode 수동 토글만으로는 '비게이머는 설정 화면을 안 연다'는 현실을 못 이긴다.
  - 제안: GameSave에 attempts: Record<episodeId, number> 한 필드만 추가해도 미니게임 플랜이 DDA를 세션 넘어 이어갈 수 있다. 지금 v2에 넣어야 마이그레이션 없이 간다.
- [medium] 긴 동사(물류·지구력)에 대한 S3 예외 규정이 없다. 오병이어 물류나 겟세마네 지구력 챌린지는 5–10분짜리가 될 수 있는데, 6분째 전화가 오면 전부 0으로 — 이건 '무손실'이 아니라 유저 체감상 명백한 손실이다. completeEpisode가 유일한 계약이라 미니게임이 중간 진행을 보고할 방법 자체가 없다.
  - 제안: 미니게임 플랜과의 인터페이스에 '3분 초과 게임은 페이즈 체크포인트 필수' 규칙과 reportPhase(episodeId, phase) 류의 선택적 계약을 추가하거나, 최소한 미니게임 길이 상한(3~7분 세션 원칙)을 이 플랜의 계약 조건으로 명문화하라.
- [medium] 내보내기/가져오기가 사실상 전체 진행 복사 배포 채널이다. '수집은 오직 플레이로만'(GDD §4)이 핵심 기둥인데, 소그룹에서 풀클리어 JSON 하나가 돌면 세트 완성 도파민과 통찰 목표의 가치가 통째로 죽는다. checksum은 손상 검출이지 변조 방지가 아니고(R7·T7이 이를 과대포장), 애들은 파일 공유를 어른보다 잘한다.

- GameSave에 에피소드별 시도 횟수(attempts) 필드 추가 — DDA가 세션을 넘어 기억되지 않으면 좌절 이탈 유저가 복귀 시 같은 벽을 다시 만남

## 박도윤(엔지니어링) — 7/10
한줄평: 실코드 기반의 드문 수준으로 구체적인 플랜이지만, 세이브 쓰기 경로의 이중 소유(persist vs autosave)와 "하위 호환" 주장과 모순되는 스키마 파괴적 변경, Zod 버전 불일치라는 내부 모순 3개를 해소하기 전에는 구현에 들어가면 안 된다.

### 이슈
- [high] 세이브 쓰기 경로의 소유권이 이중이다. §4는 'persist storage를 save/storage.ts로 교체'라 하고, 동시에 autosave.ts가 '스토어 이벤트 구독 → 디바운스 커밋'을 한다. Zustand persist는 모든 set() 호출마다 무조건 쓰기를 발동하므로 §5.3의 트리거별 디바운스 표(클리어 즉시/대화 500ms)는 persist 미들웨어로는 표현 불가능하고, 두 계층이 켜지면 이중 쓰기가 된다. 게다가 storage.ts의 setItem은 partialize된 game 문자열 하나만 받는데 SaveFile은 ink 맵+checksum+updatedAt을 합쳐야 한다 — 어댑터 안에서 스토어를 역참조해 조립하는 기형 구조가 강제된다. persist의 자체 version/migrate와 schemaVersion 마이그레이션 체인도 중복된다.
  - 제안: persist 미들웨어를 완전히 버려라. store.subscribe 기반 autosave.ts를 유일한 쓰기 경로로 삼고, 부트 시퀀스(§5.2)가 유일한 읽기 경로가 되게 하라. 이러면 §5.3 디바운스 표가 그대로 구현이 되고, SaveFile 조립·checksum 계산 시점도 한 곳으로 모인다. R2의 skipHydration 우회도 필요 없어진다.
- [high] '새 필드는 전부 optional 또는 default라 기존 episodes.ts가 깨지지 않는다'(§3.1)는 주장이 거짓이다. v0.1 verseRef는 string('누가복음 2:1-20')인데 v2는 {book,ref,display} 객체로 타입 자체가 바뀌었고, v0.1 companions(최상위 배열)는 rewards.companions로 이동했으며, scenes는 default 없는 필수 배열이다. 현 episodes.ts 12개 항목은 v2 스키마 파싱을 전부 실패한다. 테스트 #6('v0.1 데이터 → default 채워 parse 성공')은 이 스키마로는 통과할 수 없는 테스트다.
  - 제안: 하위 호환 주장을 철회하고 M2를 '일회성 콘텐츠 이관'으로 정직하게 명명하라. verseRef는 z.union([z.string(), VerseRefSchema]).transform으로 과도기를 두거나, 이관 스크립트(episodes.ts → ep*.json 변환)를 M2 산출물에 명시하라. 테스트 #6은 삭제하거나 '이관 스크립트 왕복 검증'으로 교체.
- [high] Zod 버전 불일치 + 파싱 정책 자기모순. z.looseObject(§3.2)는 Zod 4 API인데 repo는 zod ^3.24.1이다(설치본에 존재하지 않음). 그리고 §3.2는 전방 호환을 위해 '알 수 없는 키 보존'(loose)을 요구하는데 R7은 같은 세이브 가져오기에 'Zod strict 파싱'을 완화책으로 적었다 — strict는 미지 키를 거부하므로 테스트 #16(미지 필드 왕복 보존)과 정면 충돌한다.
  - 제안: zod@4 업그레이드 여부를 M1 착수 전에 결정해 플랜에 박아라(v3 유지 시 .passthrough() 사용). 파싱 정책은 계층별로 분리 명시: SaveFile 최상위는 loose(전방 호환), 렌더링되는 값은 없으므로 R7의 실방어는 'id 화이트리스트 필터 + 문자열 길이 상한'으로 정정하고 'strict 파싱' 문구를 삭제하라.
- [medium] pagehide/visibilitychange에서 '전체 플러시 즉시'(§5.3)는 보장 불가능한 약속이다. IndexedDB 쓰기는 비동기 트랜잭션이라 모바일에서 페이지가 kill되면 커밋 전에 죽을 수 있다. 저가 안드로이드 + 백그라운드 회수(S3 시나리오)가 바로 이 경우인데, 테스트 #21이 fake-indexeddb에서 통과해도 실기기에서는 최근 수 초가 유실될 수 있다.
  - 제안: pagehide 플러시는 best-effort로 명시하고, 손실 허용 창을 '마지막 장면 경계 이후'로 정의하라. 정말 지키고 싶으면 completed/companions/cards 같은 소량 핵심 필드만 pagehide 때 localStorage에 동기 미러 기록 후 다음 부트에서 병합하는 안전망을 추가하라(수십 바이트라 동기 쓰기 부담 없음).
- [medium] completeEpisode 시그니처 변경(현행 (id, companionIds: string[]) → (id, {companions, cards, insights}))이 WaterWalkGame·RewardScreen 호출부 수정을 요구하는데, §4는 '기존 5화면은 그대로 소비자'라 하고 M2 완료 기준은 '기존 화면 무수정 동작'이다. 화면 수정 범위가 플랜 내에서 은폐돼 있다.
  - 제안: M1 완료 기준에 'completeEpisode 시그니처 변경에 따른 WaterWalkGame/RewardScreen 호출부 수정' 을 명시하거나, 과도기 오버로드(두 번째 인자가 배열이면 {companions}로 승격)를 두어 정말로 무수정이 되게 하라.
- [medium] localStorage v0.1 이전(테스트 #10)이 Zustand persist 저장 포맷을 간과했다. 실제 localStorage 값은 {"state":{completed,companions,gentleMode},"version":0} 엔벨로프다. '3필드 이전 확인'만 적혀 있고 엔벨로프 언래핑·version 필드 처리가 플랜에 없다 — 실사용자 데이터가 이미 이 포맷으로 존재하므로 실수하면 M1의 완료 기준(무손실 이전) 자체가 깨진다.
  - 제안: migrations.ts의 레거시 이전 명세에 persist 엔벨로프 구조를 명시하고, 실제 브라우저에서 덤프한 원본 문자열을 픽스처로 리포에 넣어 테스트 #10을 그 픽스처로 돌려라.
- [low] checksum의 가치가 과대평가돼 있다. 사용자가 파일을 열어 편집하면 checksum도 같이 못 고칠 이유가 없고(악의 방어 불가 — R7도 인정), 우발적 손상은 JSON.parse·Zod 파싱·id 필터가 이미 잡는다. '1바이트 변조 감지'(테스트 #13)가 잡는 실세계 시나리오가 거의 없다.
  - 제안: 구현 비용이 낮으니 유지해도 되지만, '손상 검출' 대신 '진단 보조'로 역할을 격하하고 checksum 불일치 UX(계속할지 선택)를 파싱 성공 시 조용히 통과로 단순화하는 것도 고려하라.
- [low] 레거시 localStorage '30일 보존 뒤 삭제'는 이전 완료 타임스탬프 기록·만료 체크 로직을 요구하는데, 지키는 데이터가 수백 바이트다. 1인 개발에서 전형적인 마이너스 가치 기능이다.
  - 제안: 그냥 영구 보존하라. 삭제 로직 자체를 빼는 게 코드도 리스크도 준다.
- [low] 테스트 #26(10세 피험자가 안내 없이 크로스 브라우저 내보내기→가져오기 완수)은 합격 기준으로 비현실적이다. 파일 시스템 개념이 없는 연령대에 무안내 파일 이동을 요구하는 건 기능 결함이 아니라 기준 설정 오류다.
  - 제안: '보호자 동반 1회 시연 후 완수' 또는 성인 피험자 기준으로 낮추고, 10세 대상으로는 이어하기(S2) 무안내 성공만 측정하라.
- [low] EpisodeSchema의 no: max(13)이 문서 전체의 '12장'(episodes.ts 12개, M 로드맵 '콘텐츠 12장 전체')과 어긋난다. 에필로그 계획이면 어디에도 언급이 없다.

- [low] 체크섬을 '변조 차단'(T7, R7)으로 파는 건 보안 연극이다. 같은 앱이 계산하는 로컬 체크섬은 누구나 재계산해서 붙일 수 있다. 손상 감지용으로는 맞지만, 싱글플레이어 게임에서 자기 세이브 고치는 유저를 막는 데 설계 지면을 쓸 이유가 없다. 나는 오히려 세이브 만질 수 있는 게임에 호감 간다.
  - 제안: 체크섬의 목적을 '손상 감지'로만 문서에 명시하고 변조 차단 서사는 지워라. 변조 방어는 이미 잘 해놓은 'id 참조만 저장 + 렌더링 텍스트 없음'(진짜 방어)으로 충분하다.
- [low] 단일 슬롯을 '가족 공용 태블릿 요구가 검증되면'으로 미뤘는데, 이 게임의 유통 경로가 교회 소그룹·주일학교라는 걸 자기네 문서(S4의 '소그룹 나눔')가 알고 있다. 형제자매가 태블릿 하나 쓰는 집은 검증할 것도 없이 흔하다. 동생이 내 여정 위에 덮어쓰면 그게 바로 '세이브 유실 = 신뢰 유실'.
  - 제안: 다중 슬롯 구현은 미루되, 키 네임스페이스만이 아니라 부트 시퀀스에 '프로필 선택' 자리를 지금 예약해 둘 것. 나중에 슬롯 넣으려고 부트 플로우 갈아엎는 게 진짜 비용이다.

### 필수 수정
- iOS IndexedDB 퇴거(R1)에 대한 실질 대책 확정 — 익명 클라우드 백업 또는 Capacitor 전환의 확정 시점. '내보내기 소개'는 대책이 아님. 세이브 증발 한 번이면 이 게임의 핵심 자산(스크랩북 신뢰)이 끝난다.
- 가져오기 시 매니페스트 부재 id 필터링(R7) 제거 — 미지 id 보존 + 콘텐츠 id rename 맵을 마이그레이션 체인에 추가. 현재 설계는 무손실 원칙을 스스로 어긴다.
- 기기 이동 주력 플로우를 파일 내보내기에서 파일 관리 불필요한 방식으로 재설계하고, 테스트 #26을 현실적인 지표로 교체.
